# PRAVILA.md — жесткие правила проекта «Мясо Бар»

Дата фиксации: 2026-05-09.

Этот файл — обязательный регламент для человека или AI-ассистента, который работает с проектом. Перед любым изменением сначала читать `PRAVILA.md`, затем профильные планы и документацию. Менять этот файл можно только после прямого согласия владельца проекта.

## 1. Главный принцип

- Делать только то, что явно попросил владелец проекта.
- Не делать «заодно», «пока здесь», «улучшил на всякий случай» без отдельного согласия.
- Если задача не требует правки кода, не менять код.
- Если задача требует отчета, сначала изучить проект и дать отчет, а не начинать переписывать приложение.
- Любое сомнительное изменение сначала согласовать: архитектура, дизайн, зависимости, деплой, база данных, удаление файлов, переименование, массовое форматирование.

## 3. Что представляет собой проект

- `frontend/` — React 19 + TypeScript + Vite SPA.
- Публичные маршруты: главная `/`, админка `/admin/*`.
- `backend/` — Express + SQLite + Socket.IO API.
- `backend/public/` — собранная статика фронтенда, которую отдает Express через pre-compressed `.br/.gz`.
- `frontend/dist/` — production-сборка фронтенда.
- `frontend/public/sw.js` — Service Worker/PWA.
- `backend/src/db.js` — схема SQLite, bootstrap администратора, seed меню и столов.
- `frontend/src/data/menu.ts` и `frontend/src/data/tables-layout.ts` — fallback-данные, которые нельзя ломать, потому что статический деплой должен жить без backend.

## 5. Защита от mojibake и поломки русского текста

Mojibake — это порча кириллицы вида `РњСЏСЃРѕ`, `РџСЂРѕРµРєС‚`, `вЂ”`, `в„–`.

Жесткие правила:

- Все текстовые файлы с русским текстом хранить как UTF-8.
- При чтении в Windows PowerShell использовать явное чтение UTF-8: `Get-Content -Encoding UTF8 <file>`.
- Нельзя массово перекодировать файлы без согласия владельца.
- Нельзя «чинить» весь проект от mojibake автоматически, если задача этого явно не просит.
- Перед правкой русского текста проверять, что проблема реальная, а не только ошибка отображения PowerShell.
- После правки русского текста открыть измененный файл с явным UTF-8 и убедиться, что кириллица читается нормально.
- Не вставлять текст из источников, где уже есть mojibake.
- Не менять `charset`, `lang="ru"`, meta-теги и русские SEO-тексты без проверки результата.

## 8. Правила изменений

- Перед изменением прочитать затрагиваемые файлы.
- Держать изменение минимальным и локальным.
- Сохранять существующий стиль кода и CSS.
- Не трогать пользовательские или чужие незапрошенные изменения.
- Если в файле уже есть незнакомые изменения, работать поверх них аккуратно, не откатывать.
- Комментарии добавлять только там, где они реально помогают понять сложную логику.
- Для ручных правок использовать patch/edit, а не переписывать файл целиком.
- После изменения проверять затронутый сценарий: typecheck, lint, build или ручная проверка — по риску изменения.

## 9. Frontend-правила

- React 19 + TypeScript + Vite.
- TypeScript-правила из `tsconfig.app.json` не ослаблять.
- `eslint.config.js` не отключать ради прохождения проверки.
- `frontend/src/lib/api.ts` обязан отклонять non-JSON ответы, чтобы SPA fallback не ломал состояние.
- Fallback-first поведение нельзя ломать: если `/api/menu` или `/api/tables` недоступны, работают `src/data/menu.ts` и `src/data/tables-layout.ts`.
- Не добавлять тяжелые animation-библиотеки: GSAP, framer-motion, three.js, anime.js и аналоги.
- Canvas/анимации должны уважать `prefers-reduced-motion`.
- Движение делать через `transform`, `opacity`, иногда `filter`; не через `top/left` на скролле.
- Не ломать глобальные правила русской типографики: `word-break: keep-all; hyphens: none`.
- Не использовать холодные generic-акценты, синий/neon-green, случайные градиенты. Визуальный язык теплый: ember, coal, cream, gold, brass.
- Не возвращать удаленные в Phase 13 огоньки/spotlight/heatmap/pulse/dim на столики.
- Не возвращать удаленный зум на карте бронирования.

## 10. Backend-правила

- Backend — `backend/src/index.js`, Express + Socket.IO.
- Конфиг — `backend/src/config.js`, переменные через `.env`.
- База — SQLite через `better-sqlite3`, схема и bootstrap в `backend/src/db.js`.
- Авторизация админки — JWT, bcrypt, routes under `/api/auth` and `/api/admin`.
- Нельзя менять `JWT_SECRET`, bootstrap admin password, интеграции YooKassa/SMS/Telegram без явного согласия.
- Нельзя менять структуру таблиц SQLite без плана миграции.
- Нельзя удалять или пересоздавать данные в `backend/data/` без согласия.
- Public API должен отдавать JSON, не HTML.
- Ошибки API должны быть безопасными и не раскрывать секреты.

## 11. PWA и Service Worker

- `frontend/public/sw.js` менять крайне осторожно.
- При изменении SW обязательно bump версий cache namespace.
- `/socket.io/*` не кешировать.
- POST-запросы не кешировать.
- Видео и range-request streaming не перехватывать.
- Navigation — network-first с fallback на `index.html`.
- Hashed JS/CSS assets — cache-first/immutable.
- Images — stale-while-revalidate с лимитом cache.
- После изменения SW проверять install/activate/fetch flow.

## 12. Бронирование и карта столов

- Карта — реалистичная SVG-схема ресторана, не заменять на абстрактные прямоугольники.
- Столы соответствуют реальному залу: Hall 1 и Hall 2.
- Не добавлять декоративные кликабельные столы.
- При изменении столов сначала править `frontend/src/data/tables-layout.ts`, затем синхронизировать seed в `backend/src/db.js`.
- Числа столов, места, hall, shape, x/y/width/height должны быть согласованы между frontend fallback и backend seed.
- Socket.IO события `tables:updated`, `tables:created`, `tables:deleted` не ломать.

## 13. Меню, ассеты и изображения

- Меню на фронте: `frontend/src/data/menu.ts`.
- Меню в backend seed: `backend/src/db.js`.
- Фото меню и залов лежат в `frontend/public/assets/` и копируются/собираются в production assets.
- WebP — основной формат для растровых изображений.
- Новые большие JPG/PNG не добавлять без отдельного согласия и плана конвертации.
- Не менять имена ассетов, если они уже используются в коде, SW, manifest или сборке.
- При добавлении картинки проверять путь в коде и наличие файла.

## 14. Оптимизация и производительность

- Оптимизации внедрять маленькими независимыми шагами.
- Перед оптимизацией фиксировать baseline, если изменение влияет на размер, LCP, CLS, INP, TTFB или FPS.
- Не ухудшать visual quality ради «цифры», если задача не просит именно это.
- Не добавлять +50 KB ради маленького эффекта.
- Pre-compression `.gz/.br` сохранять.
- Lazy-load и code-splitting сохранять.
- RUM (`frontend/src/lib/rum.ts`, `/api/rum`) не должен ломать UX при ошибке backend.

## 15. Безопасность

- Секреты не коммитить.
- `.env` не создавать и не менять без запроса.
- Не выводить токены, ключи, SMS/API credentials в лог.
- Admin endpoints должны оставаться под `authMiddleware`.
- Login rate-limit не убирать.
- Helmet/compression/CORS менять только осознанно.
- YooKassa/SMS/Telegram integrations не включать без валидных env-переменных.

## 16. Проверки перед пересборкой

Перед любой пересборкой (`npm run build`, production build, копирование `dist` в `backend/public`, подготовка деплоя) сначала выполнить все возможные проверки для текущего состояния проекта.

Порядок:

- Проверить, что задача действительно требует пересборки.
- Проверить, какие файлы изменены и нет ли чужих незапрошенных изменений.
- Проверить UTF-8/кириллицу в измененных текстовых файлах.
- Проверить, что нет mojibake-паттернов в измененных файлах.
- Проверить TypeScript/typecheck, если затронут frontend.
- Проверить ESLint, если затронут frontend.
- Проверить backend-синтаксис/старт или relevant endpoint, если затронут backend.
- Проверить Service Worker cache version и стратегии, если затронут `sw.js`, manifest, assets или build output.
- Проверить пути ассетов, если менялись изображения, видео, manifest, preload или CSS url.
- Проверить fallback-first поведение, если менялись `api.ts`, `HomePage`, menu/tables data или public routes.
- Проверить, что `/api/*` POST и `/socket.io/*` не попали в кеш.
- Только после успешных доступных проверок запускать пересборку.

Если какая-то проверка невозможна из-за отсутствия зависимостей, sandbox, сети или внешних сервисов, это обязательно указать в отчете. Если доступная проверка падает, не делать production-пересборку без отдельного согласия владельца или без исправления причины падения в рамках задачи.

## 17. Проверки перед сдачей

Минимально:

- Перечитать измененные файлы.
- Проверить UTF-8 для русских текстов.
- Если менялся frontend: `npm run build` или минимум `npm run lint`/typecheck по ситуации.
- Если менялся backend: запуск relevant route или минимум синтаксическая проверка/старт, если зависимости установлены.
- Если менялся SW/PWA: проверить cache version и отсутствие кеширования `/api/*` POST/Socket.IO.
- Если менялись ассеты: проверить, что файл существует и путь совпадает.

Если зависимости не установлены или проверка невозможна, честно написать это в отчете.

## 20. Запрет на ложные отчёты о выполнении

ИИ **категорически запрещено**:

- Сообщать что задача выполнена, если код не был реально изменён и проверен.
- Писать «Выполнено» или «Готово» без фактического внесения изменений в файлы.
- Отмечать пункт как `[x]` в планах/чеклистах, если реальная правка не сделана.
- Имитировать выполнение: описывать «что нужно сделать» вместо реального действия.
- Выдавать план за результат: «я бы сделал X» — это не выполнение, это предложение.
- Утверждать что проверка пройдена, если команда не была запущена и вывод не получен.
- Говорить «файл обновлён» без реального вызова `str_replace` / `fs_write` и подтверждения.

**Правильное поведение:**

- Если задача выполнена — показать diff (что было → что стало) или перечислить конкретные изменения с номерами строк.
- Если проверка пройдена — показать вывод команды (exit code, ключевые строки).
- Если задача НЕ выполнена (нет доступа, ошибка, нужно уточнение) — честно сказать что не сделано и почему.
- Если пункт плана помечается как выполненный — указать в каком файле, какая строка, какой результат проверки.

**Нарушение этого правила = потеря доверия владельца. Лучше честно сказать «не смог» или «нужно уточнение», чем выдать пустой результат за работу.**
