# Error handling — единая модель

Основа — рекомендации TypeScript team, Martin Fowler, Kent C. Dodds, Node.js best practices. Адаптировано под наш React 19 + Express + SQLite стек.

## Принципы

1. **Ошибки — это данные, а не исключения**. Возвращать, а не бросать, где возможно.
2. **Никогда не ловить и не глотать ошибку молча**. Минимум — `console.warn` с контекстом.
3. **Пользователь видит человеческий текст**. Никогда не показывать stack trace или код ошибки с сервера.
4. **Fallback-first**: если что-то упало, UI остаётся рабочим на локальных данных.

## Frontend

### Discriminated union для async-состояний

```tsx
type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'ok'; data: T }
  | { status: 'error'; error: Error }
```

Не использовать `{ loading: boolean, error: string | null, data: T | null }` — это развод на баги.

### API-запросы

- `fetch` всегда в `try/catch`.
- Проверять `response.ok` до `response.json()`.
- `api.ts` уже кидает ошибку на non-JSON ответы (SPA fallback). Не ломать.
- На ошибку — показать человеческий тост, **не** «Network Error» и **не** stack.

### Границы (Error Boundaries)

- Ставить на lazy-чанках (CartDrawer, TableMap, BookingDialog, AdminApp).
- Fallback UI — тёплый, с кнопкой «попробовать снова».
- Логировать через `console.error` с контекстом — попадёт в RUM (planopt J48 добавит Sentry).

### Формы

- Валидация при blur + при submit.
- Ошибки полей — `aria-invalid="true"` + `aria-describedby` со ссылкой на текст.
- После отправки — `disabled={loading}` пока запрос идёт.
- После успеха — тост + reset.
- После ошибки — тост + оставить введённые данные.

### Оффлайн

- `navigator.onLine === false` → не пытаемся убивать запрос, сразу в очередь (уже сделано для бронирований в `frontend/src/lib/api.ts`).
- Автофлэш при `online` event.

### Не делать

- `throw new Error('Ошибка 500')` — безграмотно.
- `catch (e) {}` — молча глотаемая ошибка.
- `alert(...)` — никогда.
- `console.log` в проде без префикса — мусор.

## Backend

### Формат ответа с ошибкой

Всегда JSON:

```json
{ "error": "Пользовательское сообщение" }
```

Никогда не отдавать stack, путь к файлу, SQL-запрос, токен.

### HTTP-коды

| Код | Когда использовать                              |
| --- | ----------------------------------------------- |
| 200 | OK                                              |
| 201 | Created (опц., можно 200)                       |
| 204 | No Content (для `/api/rum` и подобных)          |
| 400 | Валидация тела / query                          |
| 401 | Нет/битый токен                                 |
| 403 | Есть токен, но прав нет / CORS запрет           |
| 404 | Нет ресурса                                     |
| 409 | Конфликт состояния (стол уже забронирован)      |
| 429 | Rate-limit                                      |
| 500 | Что-то поломалось на бэке                       |

### Middleware-обёртка

В `index.js` глобальный error handler — уже есть. Не убирать. Дополнительно:

- Для CORS/Socket.IO — 403 с читаемым текстом.
- Для остального — 500 + `console.error('[server] error:', err)`.
- Никогда не `res.send(err.stack)`.

### SQLite

- `db.prepare().run()` может бросить — оборачивать там, где ошибка не фатальна (пример: `insert rum_events`).
- Схема через `CREATE TABLE IF NOT EXISTS` — идемпотентная, не падает на повторном bootstrap.

### Rate-limit

- `express-rate-limit` сам возвращает 429 с дефолтным сообщением.
- Кастомизировать `message: { error: 'Слишком много запросов, подождите 10 минут' }`.

### Интеграции (YooKassa / SMS / Telegram / VK)

- Ошибка интеграции **не должна** ломать основной flow.
- Пример: бронь сохранена в БД → уведомление в Telegram упало → пользователь всё равно видит успех.
- Всё через `.catch(() => {})` с локальным `console.warn`.

### Сокеты

- Попытка emit в `io` на отключённом сокете — не бросать в транзакцию.
- `io?.emit(...)` (optional chaining) везде.

## Что логировать, а что нет

### Логировать

- Все 5xx.
- Rate-limit срабатывания (для детекции атак).
- Неудачные логины (для детекции brute-force).
- Ошибки миграции БД.
- Отвалившиеся интеграции.

### Не логировать

- Пароли, JWT-токены, API-ключи, SMS-коды, VK-токены.
- Тело `/api/rum` (может разнести диск).
- Тело `/api/orders` целиком — только `orderId` и `total`.

## Тестирование ошибок вручную

- DevTools → Network → Offline → попробовать бронь → должна встать в очередь.
- DevTools → Network → Throttling → Slow 3G → проверить UX с лоадерами.
- Бэкенд уронить → фронт должен остаться на fallback-данных.
- Отправить неправильное тело на `/api/bookings` → получить 400 с читаемой ошибкой.
