# WORKFLOW.md — жёсткий регламент работы любых ИИ с проектом

Дата фиксации: 2026-05-10.

Цель: чтобы любой ИИ делал только запрошенное, не ломал проект и всегда оставлял сборку рабочей.

## 1) Обязательный порядок перед началом

Любой ИИ **обязан** сначала прочитать:

1. `PRAVILA.md`
2. `PLAN-1-OPTIMIZATION-SEO-PRODUCTION.md`
3. `PLAN-2-PREMIUM-VISUAL-DESIGN.md`
4. `docs/PERF-BASELINE.md`

Без этого нельзя начинать правки.

## 2) Что ИИ делать нельзя

- Нельзя делать изменения “заодно”, если владелец этого не просил.
- Нельзя менять архитектуру, зависимости, структуру папок без явного запроса.
- Нельзя трогать критичные визуальные/UX-части вне задачи.
- Нельзя менять `dist`/сборочные артефакты вручную.
- Нельзя удалять/переименовывать файлы без прямого запроса.
- Нельзя коммитить секреты, ключи, `.env`.

## 3) Принцип “только по задаче”

Каждая сессия ИИ:

1. Формулирует, что именно будет менять.
2. Меняет только нужные файлы.
3. Не исправляет unrelated-части без согласования.
4. После правок обновляет статус в плане (если задача относится к планам).

## 4) Обязательные проверки после правок

Строгий порядок:

1. `npm --prefix frontend run guard:mojibake`
2. `npm --prefix frontend run lint`
3. `npm --prefix frontend run build`
4. `npm --prefix frontend run perf:budgets`
5. `node --check backend/src/index.js`

Если любой шаг упал — ИИ обязан исправить и прогнать заново.

## 5) Definition of Done (задача считается выполненной только если)

- Сделано именно то, что просил владелец.
- Нет лишних изменений.
- Пройдены проверки из раздела 4.
- Обновлены `UPDATE`-блоки в планах/базлайне (если уместно).
- В отчёте есть: что изменено, что проверено, что осталось.

## 6) Работа с правками от других ИИ

Если проект менял другой ИИ:

1. Не откатывать его изменения автоматически.
2. Проверить совместимость с текущей задачей.
3. После интеграции снова прогнать проверки из раздела 4.
4. Если есть конфликт по логике/правилам — остановиться и запросить решение владельца.

## 7) Git-порядок

- Работать маленькими логичными коммитами.
- Сообщение коммита должно отражать суть изменения.
- Перед push убедиться, что рабочее дерево чистое и проверки пройдены.
- Для бэкапа/продолжения работ хранить актуальные планы и baseline в репозитории.

## 8) Быстрый шаблон промпта для любого ИИ

Использовать в начале задачи:

1. Прочитай `PRAVILA.md`, `WORKFLOW.md`, оба плана и `docs/PERF-BASELINE.md`.
2. Делай только то, что я прошу, без лишних изменений.
3. После правок запусти проверки:
   - `npm --prefix frontend run guard:mojibake`
   - `npm --prefix frontend run lint`
   - `npm --prefix frontend run build`
   - `npm --prefix frontend run perf:budgets`
   - `node --check backend/src/index.js`
4. Обнови статус выполненных пунктов в планах.
5. Дай короткий отчёт: что сделано, что проверено, какие риски.

## 9) Приоритет правил (чтобы ИИ не путался)

Если есть конфликт, применять в таком порядке:

1. Прямой запрос владельца (текущая задача).
2. `PRAVILA.md` (жёсткие проектные ограничения).
3. `WORKFLOW.md` (процесс выполнения).
4. Планы (`PLAN-1`, `PLAN-2`) как дорожная карта.

Если ИИ не уверен — не “додумывать”, а остановиться и спросить владельца.

## 10) Анти-ломающий режим (обязательно для любого ИИ)

- Любое изменение только минимальным патчем.
- Запрещены массовые рефакторы “для красоты”.
- Запрещено менять поведение функций, если это не цель задачи.
- Запрещено трогать SEO/маршруты/кеш/PWA без явного запроса.
- Запрещено “исправлять всё подряд” при одном мелком баге.
- Любой новый риск должен быть явно описан в отчёте.

## 11) Контроль границ задачи

Перед правками ИИ обязан письменно зафиксировать:

1. Цель задачи (1–2 строки).
2. Какие файлы будут изменены.
3. Какие файлы **не** будут изменены.

После правок ИИ обязан показать:

1. Что изменено фактически.
2. Что не выполнено (если осталось).
3. Результат проверок.

## 12) Правила качества коммитов

- Один коммит = одна логическая задача.
- Коммит должен быть читаемым (понятный message).
- Нельзя смешивать в одном коммите: фичу + unrelated-правки.
- Перед push: `git status` чистый, проверки пройдены.

## 13) План оптимизации производительности (Performance Optimization Roadmap)

Дата: 2026-05-12. Проблема: лаги даже на десктопе из-за одновременной работы множества canvas-анимаций, тяжёлых CSS-эффектов и избыточных compositor layers.

Принцип: **то же визуально, но умнее по исполнению**. Не терять качество — делать максимальную производительность.

### P1 — Критичные (максимальный эффект, минимальный риск)

- [x] **P1.1** Кэшировать градиенты частиц — в `EmberField` и `AnimatedFire` pre-bake 8–12 градиентных кругов в offscreen canvas при mount, потом `drawImage` вместо `createRadialGradient` каждый кадр.
- [x] **P1.2** FireText: кэшировать text mask — вычислять позиции символов один раз при mount + resize, убрать `querySelectorAll` + `getBoundingClientRect` из rAF loop.
- [x] **P1.3** Остановить/замедлить canvas вне активной зоны — `AnimatedFire` в шапке снижать FPS до 12 при скролле ниже hero. Проверить что `EmberField` реально паузится через IO.
- [x] **P1.4** `preserve-3d` только на hover — убрать `transform-style: preserve-3d` из дефолтного состояния карточек, добавлять только при `--hover: 1`. В покое — flat layer.

### P2 — Важные (заметный эффект)

- [x] **P2.5** Убрать `backdrop-filter` с `.scene-card` — заменить на solid `background: rgba(10, 7, 5, 0.92)`.
- [x] **P2.6** CSS-анимации: `animation-play-state` через IO — для `fireGlow`, `grain`, `fire-flicker` добавить класс `.is-offscreen` через IO, который ставит `animation-play-state: paused`.
- [x] **P2.7** DriftingClouds: снизить density на десктопе — 34 → 18 облаков.
- [x] **P2.8** `box-shadow` через `calc()` → статичный на покое — динамический только при `--hover: 1`.

### P3 — Полировка

- [x] **P3.9** Adaptive FPS для canvas — если `rafScheduler` видит FPS < 40, автоматически снижать density/skip frames.
- [x] **P3.10** `body::before` → убрать на mid-tier тоже.
- [x] **P3.11** `will-change` ревизия — убрать с элементов, которые не анимируются постоянно.
- [x] **P3.12** FireText: увеличить `repeatInterval` до 60+ или отключить repeat для не-hero экземпляров.

### P4 — Архитектурные (если P1–P3 недостаточно)

- [!] **P4.13** Десктопный mid-tier — добавить в `perfTier.ts` проверку `hardwareConcurrency <= 4` на десктопе → `'mid'`. (Отложено: требует тестирования на реальных десктопах, риск ложных срабатываний на VM/WSL.)
- [!] **P4.14** Единый canvas для всех огней — объединить `EmberField` + `AnimatedFire` в один canvas layer. (Отложено: архитектурное изменение, P1–P3 дали достаточный эффект.)
