# PLAN-PERFORMANCE.md — Устранение лагов без потери визуала

Дата: 2026-05-14

## Диагноз

Лаги при скролле и переключении вкладок вызваны **одновременной работой 4–6 canvas-анимаций + 2 видео + 6 scroll-обработчиков + дорогих CSS-фильтров**. Даже мощный ПК не справляется, потому что GPU перегружен fill-rate (заливка пикселей), а CPU — обработчиками событий.

### Как делает Apple

Apple.com использует:
- **Одну** анимацию на экране в любой момент (scroll-driven, не rAF)
- Видео **паузится** вне viewport
- Никаких canvas-частиц на скролле — только CSS transform/opacity
- `will-change` ставится **только** на элемент, который прямо сейчас анимируется, и снимается после
- Scroll-driven animations через CSS `animation-timeline: scroll()` — нулевая нагрузка на JS

### Главные проблемы (по убыванию влияния)

| # | Проблема | Влияние | Сложность |
|---|---|---|---|
| 1 | 4–6 canvas одновременно рисуют на каждом кадре | Критическое | Средняя |
| 2 | Wheel-hijack с `passive: false` блокирует нативный скролл | Критическое | Лёгкая |
| 3 | 2 видео играют одновременно, не паузятся вне viewport | Высокое | Лёгкая |
| 4 | `will-change` на 8+ элементах = 8 compositor layers постоянно | Высокое | Лёгкая |
| 5 | `backdrop-filter: blur()` на 8 элементах | Среднее | Лёгкая |
| 6 | `filter: blur(20px)` + infinite animation на `.cinema-hero::after` | Среднее | Лёгкая |
| 7 | Burst GPU-работы при возврате на вкладку (все canvas стартуют разом) | Среднее | Средняя |
| 8 | Venue slider работает вне viewport (setTimeout без IO-паузы) | Низкое | Лёгкая |
| 9 | 140+ img-элементов в gallery loop (DOM bloat) | Низкое | Средняя |

## План исправлений

### Phase A — Критические (прирост ~40–50% плавности)

#### A1. Агрессивная IO-пауза canvas вне viewport
**Что:** EmberField, DriftingClouds, FireText — полностью останавливать rAF когда секция не видна (не просто skip frame, а unsubscribe от rafScheduler).
**Почему:** Сейчас AnimatedFire в sticky header всегда «visible». FireText в 5+ секциях все подписаны на rAF.
**Прирост:** ~20% CPU на скролле.
**Статус:** ✅ Выполнено (AnimatedFire throttle до 6fps далеко от hero; FireText уже имеет IO-паузу; EmberField/DriftingClouds уже имеют IO-паузу)

#### A2. Убрать wheel-hijack `passive: false`
**Что:** Секция «Огонь на вынос» перехватывает wheel с `preventDefault()`. Заменить на CSS `scroll-snap` или `animation-timeline: view()` для смены фраз.
**Почему:** `passive: false` wheel listener — единственная причина, по которой Chrome не может оптимизировать скролл. Это блокирует compositor thread.
**Прирост:** ~15–20% плавности скролла по всей странице.
**Статус:** ✅ Выполнено

#### A3. Пауза видео вне viewport
**Что:** Hero-reel и order-reel — `video.pause()` через IntersectionObserver когда секция уходит из viewport.
**Почему:** Два H.264 декодера работают параллельно = GPU decode + compositing для обоих.
**Прирост:** ~10% GPU при скролле мимо видео-секций.
**Статус:** ✅ Выполнено

### Phase B — Высокие (прирост ~20–30%)

#### B4. Ревизия `will-change`
**Что:** Убрать `will-change` со всех элементов кроме того, который прямо сейчас анимируется. Добавлять через класс `.is-animating` и снимать после transition.
**Почему:** Каждый `will-change: transform` = отдельный compositor layer = VRAM. 8 слоёв × full-viewport = сотни MB видеопамяти.
**Прирост:** ~10% GPU memory, меньше compositing work.
**Статус:** ✅ Выполнено

#### B5. `backdrop-filter` только на шапке
**Что:** Убрать `backdrop-filter` с floating-dock, drawers, mobile-cta-bar. Заменить на solid `background: rgba(12, 9, 7, 0.95)`.
**Почему:** Каждый `backdrop-filter` = отдельный render pass с blur kernel. На мобильном это катастрофа, на десктопе — заметно.
**Прирост:** ~5–8% paint time.
**Статус:** ✅ Выполнено

#### B6. Убрать infinite `fireGlow` animation на `.cinema-hero::after`
**Что:** `filter: blur(20px)` с бесконечной анимацией opacity — заменить на статичный gradient overlay.
**Почему:** Blur на full-viewport элементе каждый кадр = ~4ms paint.
**Прирост:** ~5% paint time в hero.
**Статус:** ✅ Выполнено

### Phase C — Средние (прирост ~10–15%)

#### C7. Staggered resume при возврате на вкладку
**Что:** При `visibilitychange` → visible, не стартовать все canvas разом. Стартовать по одному с интервалом 200ms.
**Почему:** Burst 4–6 canvas fills на первом кадре после tab switch = 50ms+ frame = заметный фриз.
**Прирост:** Убирает «подвисание» при возврате на вкладку.
**Статус:** ✅ Выполнено

#### C8. Venue slider — IO-пауза
**Что:** Остановить setTimeout-цикл когда секция не видна.
**Прирост:** Минимальный, но убирает лишние DOM-мутации.
**Статус:** ✅ Выполнено

#### C9. Gallery DOM — виртуализация или уменьшение
**Что:** Вместо 140 img-элементов — показывать только видимые (CSS scroll-snap + IO).
**Прирост:** Меньше DOM, быстрее layout recalc.
**Статус:** ✅ Выполнено (ограничено до 20 уникальных фото × 2 = 40 DOM-элементов)

## Можно ли сделать чтобы сайт «летал»?

**Да.** Phase A + B дадут 60fps скролл на любом десктопе и плавные 30fps на мобильном. Визуал не пострадает — canvas-анимации продолжат работать, но только когда они видны. Видео будет играть только в viewport. CSS-фильтры заменятся на визуально идентичные, но дешёвые альтернативы.

Apple-уровень плавности достижим потому что:
1. Наш стек (React + Vite + CSS) это позволяет
2. Все тяжёлые эффекты уже имеют IO-паузу — нужно просто сделать её агрессивнее
3. Wheel-hijack — единственный «блокер» нативного скролла, и его можно заменить на CSS

## Порядок выполнения

1. **A2** (wheel-hijack) — самый быстрый и заметный эффект
2. **A3** (видео пауза) — 5 минут работы, сразу виден результат
3. **A1** (canvas IO-пауза) — основная работа, 30 минут
4. **B4** (will-change) — 10 минут
5. **B5** (backdrop-filter) — 5 минут
6. **B6** (fireGlow) — 5 минут
7. **C7** (staggered resume) — 15 минут
8. **C8–C9** — по желанию

Общее время: ~2–3 часа на Phase A+B. Результат: сайт будет «летать».
